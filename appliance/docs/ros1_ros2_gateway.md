# Explicit ROS1/ROS2 gateway

Noetic runs on the Ubuntu host; Humble lives in the container. Official dynamic_bridge requires ROS1 and ROS2 build-time message dependencies in one ABI-compatible environment. No prebuilt/validated bridge for the 20.04 Noetic / 22.04 Humble combination was found. The repositories contain no YHS bridge. rosbridge adds JSON/WebSocket and broad topic/shell surface; it is unnecessary for this small same-host data contract.

Implemented: two independent Python endpoints with Unix stream socket mounted at ~/agt/run/gateway.sock. ROS1 endpoint imports rospy/genpy only; ROS2 endpoint imports rclpy/rosidl only. No cross-distro compilation, network discovery, LiDAR bridging or custom binary ABI. Permission 0600; run directory 0700; matching host/container UID. Framing is bounded JSON lines with session UUID and monotonically increasing command sequence. ROS2 subscribes **only** to Motion Guard output /mux/cmd_vel; Qt speed is /agt/hmi/cmd_vel upstream of the existing guard. No endpoint publishes TF.

ROS1 -> ROS2: standard nav_msgs/Odometry preserving timestamp, header frame, child frame, pose/twist and covariances; chassis std_msgs/String (driver adapter must normalize vendor fields to JSON); estop std_msgs/Bool (true=stop). Required ROS1 topic names are null in profiles/yhs/topics.yaml until the real driver is audited. CAN status is read on host; do not infer CAN health merely from a socket connection.

ROS2 -> ROS1: geometry_msgs/Twist, linear.x/angular.z. Fixed 50 Hz capability at both endpoints. FIFO queue_size=1, no offline command queue. Disconnect resets velocity, session and estop; reconnect requires fresh status and fresh guarded command. ROS1 outputs zeros when connection, command, chassis or estop status is stale. command_timeout_sec is supplied by measured profile; production cannot start motion with null timeout. Driver watchdog must be separately verified: if ROS1 endpoint itself dies it cannot publish zeros. A software watchdog cannot replace the hardware/driver timeout.

`./agt up` starts host control and, when the profile is complete and /opt/ros/noetic/setup.bash exists, the ROS1 endpoint. Host environment must include the installed vendor ROS1 driver workspace (or launch it separately as specified by that driver's audit). A generic driver is not invented. CAN up/down use fixed ip argv from validated profile, never shell text, and log every operation. Without passwordless authorization, GUI reports the exact host command to execute; sudo -n cannot prompt inside Qt. No privileged container or Docker socket mount is used.

Cloud evidence: pure framing/sequence/watchdog tests plus a same-host 50 Hz mock socket benchmark with measured round-trip distributions. This is not real CAN or chassis latency. Field benchmark must verify odom ~50 Hz, cmd_vel capability, command/estop timestamps, unplug/replug, ROS2 kill, ROS1 gateway kill and actual driver stop timeout. See real_robot_acceptance.md.
